From Telepathic Development to Contract-Oriented: Why Spec and Unit Tests are Life Savers

發表於 2026-02-25 分類於 Tech Sharing

Looking back at my time in my previous company, the development environment was quite “wild.” We lacked formal development standards—even PEP8, Linters, or Formatters were only reluctantly introduced in the later stages of projects. At that time, our most hardcore way of communicating was simply looking at the Database.

Back then, there was no such thing as an API Spec. The only intersection between front-end and back-end developers was:

“Hey, I’ve opened the new fields for that feature in the UserStatus table.”
“The type is VARCHAR(10), go ahead and connect to it yourself.”

We treated the database as the “Source of Truth,” completely ignoring the massive deviations that can occur when different program logics interpret the same data.

1. A Painful Lesson: When “Booleans” Become a Mystery

Without a defined Spec, development is like playing an expensive guessing game. One example that stands out is the definition of a status field.

During our verbal discussion, everyone agreed it was a simple toggle concept. However, when it came to implementation:

  • Back-end Engineer: Intuitively returned a Boolean True / False.
  • Front-end Engineer: Based on past experience, wrote the logic to expect strings "Y" / "N".

The result? The front-end display was permanently broken. Both sides sat staring at the screen during debugging: “I thought we agreed it would be like this…” This kind of low-level error caused by a communication breakdown is exactly why a standard OpenAPI Spec is needed as a development contract.

2. OpenAPI Spec: No More Relying on Intuition

To avoid the tragedies mentioned above, defining a clear YAML document is the first step. It defines not only types but also formats and Enums.

3. Beyond Specs, Why Do We Need Unit Tests?

While Specs solve external communication issues, internal logic correctness relies on Unit Tests.
Many people feel that writing tests is a waste of time. In reality, unit tests are meant to catch those “I thought it was fine” moments. A good test shouldn’t just check the “Happy Path”; it should rigorously verify the following scenarios:

  1. Happy Path: Ensuring the system works as expected when input is correct.
  2. Edge Cases:
  • What happens if the API receives a null value?
  • What happens if a string length exceeds the VARCHAR limit set in the DB?
  1. Boundary Testing:
  • Does the logic collapse when a numerical value is 0 or negative?
  • How does the system behave when an array length is exactly at its upper or lower limit?

Comprehensive unit tests give us the confidence (the “bottom line”) to refactor or add new features without breaking existing ones.

From Writing Code to Building Stable Systems

Moving from having zero standards to learning to write the Spec before starting—and thinking about test cases before writing logic—has been the biggest shift in my development mindset. The Spec is a commitment to the outside world; Unit Testing is self-discipline for the inside.
Good software engineering isn’t about who writes code the fastest; it’s about who can ensure the system remains stable and maintainable one, or even three years down the road.
